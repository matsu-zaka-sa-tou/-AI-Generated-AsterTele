Bug #3 通话建立日志重复 / ACK 无转发日志 / 无音频 / 双端 Android
问题

200 OK 转发给主叫后，被叫的 200 OK 仍持续重传（应用层无去重）；

ACK 从未到达服务端 → 无转发日志；

两个 Android Zoiper 客户端无法建立音频通道。

关键发现

客户端的 ACK/BYE 是根据 200 OK 中的 Contact 和 Record-Route 来路由的。

如果 Contact 指向服务器直连 IP，但客户端在 NAT 后面，ACK 发不到服务器；

如果缺少 Record-Route，客户端可能把 ACK 发到被叫的 Contact 地址而非服务器。

解决

1. 在转发响应中添加 Record-Route 头（使用 AdvertisedAddress），强制后续请求路由到服务器

2. 设置 Callee200OkProcessed=true 实现去重，重传时直接发送缓存的响应

3. 添加 B2BUA 生成的 To tag（B2buaToTag）到所有转发响应

4. 添加服务器 Contact 头到转发响应

Bug #4 8003 摘机仍显示 "Calling" / 挂断不同步 / 日志需求
问题 1

8003 摘机（200 OK）后，8002 仍显示 "Calling" — 说明 200 OK 未正确转发到主叫

问题 2

8002 挂断后 8003 不同步挂断 — BYE 转发/路由失败

问题 3

日志需要输出到 exe 同目录而非控制台

根本发现

SIPSorcery UAS 事务引擎吞噬了 ACK 和 BYE！

在 stateful 模式下，SIPSorcery 的 UAS 事务会自动匹配 ACK/BYE，但不会触发应用层事件。

这意味着 SIPTransportRequestReceived 根本收不到 ACK 和 BYE。

关键修复 切换到 Stateless 模式 — 禁用事务引擎
方案

将 SIPTransport 从有状态模式改为 stateless: true，禁用事务引擎，所有 SIP 消息直接触发应用层事件。

var transport = new SIPTransport(stateless: true, Encoding.UTF8, Encoding.UTF8);
附带问题

Stateless 模式下没有事务层去重，需要自己处理：

• INVITE 重传去重

• BYE 重传去重

• 200 OK 重传去重

• ACK for non-2xx 需要手动发送（原来事务引擎会自动处理）

根因分析 ACK/BYE 路由不到服务器的真正原因
网络拓扑
8002 (192.168.40.100)  ←──同子网──→  服务器 (192.168.40.102)
8003 (192.168.0.110)   ←──NAT──→   路由器 (192.168.40.1) ←──端口转发──→ 服务器
核心问题

AdvertisedAddress = 192.168.40.1（路由器 IP）被用于所有客户端的 Contact/Record-Route。

• 跨子网客户端（8003）：ACK 发往 192.168.40.1 → 端口转发到服务器 ✅

• 同子网客户端（8002）：ACK 也发往 192.168.40.1 → 发到路由器而非服务器 ❌

路由器端口转发是单向的（WAN → LAN），同子网到路由器的 UDP 不会转发回服务器！

次要发现

• 非 2xx 响应（486 BusyHere）也会无限重传 — stateless 模式下没有事务引擎自动发 ACK for non-2xx

• Proxy ACK 延迟约 1.5 秒（等了两次 200 OK 重传才发）

• 主叫的 BYE 同样到不了服务端，导致挂断时只有一端能正常释放

终极修复 四大修复落地 — 智能路由 + 立即 ACK + non-2xx ACK + BYE 超时

根据客户端来源网络选择 Contact/Record-Route 地址：

同子网客户端 (192.168.40.0/24) → Contact = 192.168.40.102 (服务器直连IP)
跨子网客户端 (192.168.0.0/16)  → Contact = 192.168.40.1   (路由器IP)

实现 IsSameSubnet() + GetContactEPForClient()，在 INVITE / 200 OK / BYE / ACK 构建时动态选择地址。

同子网客户端的 ACK/BYE 现在直连服务器 IP，不再绕路到路由器。

修复 2：Proxy ACK 立即发送

首次转发 200 OK 给主叫后，立即发送 Proxy ACK 给被叫。

原来：等重传 #2 才发（延迟 ~1.5 秒）→ 被叫 200 OK 重传 2-3 次

现在：随首次 200 OK 同时发出 → 被叫在 T1 (~500ms) 内收到 ACK，停止重传

修复 3：ACK for non-2xx

新增 SendAckForNon2xxToCallee() 方法。

当收到被叫的 486/487/4xx/5xx 响应时，立即代替主叫向被叫发 ACK for non-2xx，停止重传。

Stateless 模式下 UAS 事务引擎不会自动做这件事，必须手动处理。

修复 4：BYE 超时重传 + 强制清理

HandleBye 不再立即移除会话，改为 CallState.Disconnecting。

清理定时器每 5 秒重传未确认的 BYE（最多 3 次），20 秒后强制清理。

BYE 发出 → 5s 未确认 → 重传 #1 → 5s → 重传 #2 → 5s → 重传 #3 → 5s → 强制清理
总超时 = 20 秒
Bug #5 生产反馈：有几率无法同时挂断
问题

实际部署后反馈：双方同时按挂断时，有几率一方无法成功挂断，仍停留在通话界面。

根因分析

竞态条件 1：ByeProcessed 全局标志导致第二方 BYE 被吞。

原代码用单个 ByeProcessed 标志控制重传去重，但双方同时 BYE 时，第二方的 BYE 是不同 Call-ID 的独立挂断请求，却被当作重传忽略。

8002 BYE (callerCallId) → ByeProcessed=true, 转发 BYE 给 8003
8003 BYE (calleeCallId) → ByeProcessed=true → 当作重传, 不转发

竞态条件 2：BYE 的 200 OK 响应未被处理。

OnSipResponseReceived 只处理被叫 INVITE 响应转发，完全忽略 BYE 的 200 OK。服务端不知道 BYE 是否送达，只能等 20 秒超时强制清理。

修复 双边挂断追踪 + BYE 200 OK 响应处理
修复 1：双边挂断独立追踪

废弃全局 ByeProcessed，改用 CallerHungUp / CalleeHungUp 独立追踪两侧挂断状态。

BYE 到达时只标记对应侧已挂断，仅当另一侧尚未挂断时才转发 BYE。

8002 BYE → CallerHungUp=true, 转发 BYE 给 8003
8003 BYE → CalleeHungUp=true, 不重复转发 (8002已挂)
双方均 HungUp → 立即清理会话
修复 2：BYE 200 OK 响应处理

新增 HandleBye200Ok() 方法，在 OnSipResponseReceived 中识别 BYE 的 200 OK。

收到后标记 Bye200OkReceived=true，停止重传，并标记对端已挂断。若双方都已挂断，立即清理会话。

服务器发 BYE → 对端回 200 OK → Bye200OkReceived=true → 确认送达, 停止重传
里程碑 SIP Trunk 外呼 — 对接中国电信 IMS

新增 SipTrunkManager.cs 模块，实现与运营商 SIP Trunk 的对接，让内机拨打外线号码（按 9 出局）。

核心功能

1. REGISTER 注册：向运营商 P-CSCF (172.26.160.38) 注册 Trunk 号码，含 401 Digest 重认证

2. 外呼 INVITE：内机按 9 出局时，B2BUA 向运营商发起 INVITE，含 SDP 透传

3. 183 Session Progress：运营商返回早期媒体（回铃音/语音提示），透传给内机

4. 入站 INVITE：运营商呼入时，DID 映射到内机并振铃

5. 呼叫转移：Busy / NoAnswer / Unconditional 三种转移模式

6. DTMF：SIP INFO 方式的 DTMF 透传

遗留问题

纯信令 B2BUA 模式下，外呼 INVITE 的 SDP 中 c= 地址被替换为 OutboundAddress (172.48.242.167)，但 RTP 端口没有路由器 NAT 转发 → 运营商往公网 IP 发的 RTP 包被路由器丢弃 → 内机听不到早期媒体/语音提示。

Bug #6 外线通话 BYE 路由错误 — Request-URI 指向自身
问题

外线通话中，运营商发 re-INVITE 后 BYE 路由出错。被叫侧挂断时，AsterTele 向主叫侧发 BYE 的 Request-URI 用了 session.CallerInvite.URI，指向自己的 Contact 地址而非运营商的 Contact。

同时，入站通话中运营商发 re-INVITE（更新会话参数），被错误当作 INVITE 重传处理，导致运营商 24 秒后主动 BYE 挂断。

根因分析

BYE 路由：B2BUA 构造 BYE 时未使用对方在 200 OK/Contact 中声明的地址，而是用了 INVITE 的原始 URI。当通话经过 re-INVITE 后，运营商的 Contact 可能已变化。

re-INVITE 误判：HandleInvite 中 existingByCaller!=null 分支无条件走重传逻辑，没有做 CSeq 比较。CSeq 递增的 re-INVITE 被当作 CSeq 相同的重传直接丢弃。

修复 1：缓存 Contact URI

在 CallSession 中新增 CallerContactUri / CalleeContactUri 字段，在创建会话时（CreateSession）和收到 200 OK 时（ForwardCalleeResponse）保存运营商/被叫的 Contact URI。

SendByeToCaller 和 SendByeToCallee 使用缓存的 Contact URI 构造 BYE 的 Request-URI。

修复 2：CSeq 区分 re-INVITE 与重传

在 CallSession 中缓存原始 INVITE 的 CSeq（CallerInviteCSeq 字段）。HandleInvite 的 existingByCaller 分支中：

CSeq 相同 → 重传, 重发最后响应
CSeq 递增 → re-INVITE, 调用 HandleTrunkReInvite
修复 3：路由集 (Route Set) 支持

SendByeToCaller / SendByeToCallee 构造 BYE 时，按 RFC 3261 将 SIPRouteSet 的 reversed 路由集添加为 Route 头，确保 BYE 沿原对话路径路由回运营商。

Bug #7 RTP 中继方案 — 回声环路，实测失败并回滚
问题

为解决「内机打外机，外机拒接时内机听不到提示音」的核心问题，实现了完整的 RTP 中继方案：RtpRelaySession.cs（双向 RTP/RTCP UDP 转发）+ SdpModifier.cs（SDP 修改工具）。

实测结果：只能听到自己说的话（回声/环路），相当于 TX/RX 短接。

失败根因分析

单 socket 双向转发的方向判断不可靠。

RtpRelaySession 用一个 RTP socket 接收双方包，通过 IsFromCaller() 判断方向后转发。但：

1. 初始阶段（双方都未发送过包时），方向默认假设「来自分机侧」，第一个到达的包方向可能误判

2. NAT 环境下源地址不可靠，内机经 NAT 后的源端口与 SDP 声明端口不一致

3. 方向一旦误判，后续所有包都沿错误方向转发，形成回声环路

处置：完整回滚

删除了 RtpRelaySession.cs 和 SdpModifier.cs，CallManager.cs / SipSoftSwitch.cs / SipOptions.cs / appsettings.json / Program.cs 均恢复原状。编译验证通过，0 错误 0 警告。

路由器 RTP 端口转发也已删除。

后续方向

方案 A：用两个独立的 RTP socket（分机侧一个、运营商侧一个），彻底避免方向判断

方案 B：使用 SIPSorcery 自带的 RTPChannel / RTPSession 做 RTP 中继

方案 C：轻量级 UDP 转发但用两个 socket 分别绑定不同端口

💡 关键经验教训

SIPSorcery stateless 是必需的，但代价是自己处理一切去重。

Stateful 模式下 UAS 事务引擎吞噬了 ACK/BYE 事件，但自动处理了去重、重传、non-2xx ACK。切换到 stateless 后这些都要自己实现。

AdvertisedAddress 不是万能的——同子网客户端不需要 NAT 地址。

一刀切地把所有 Contact/Record-Route 设为路由器 IP，会让同子网客户端的 ACK/BYE 错误路由到路由器。必须按客户端网络拓扑动态选择。

Via 头不能替换——客户端用它匹配 INVITE 事务。

曾尝试替换 Via 为服务器地址来路由 ACK，结果客户端无法匹配 200 OK → 通话完全无法建立。Via 必须保留原始 INVITE 的值。

双边 BYE 竞态是 B2BUA 最容易忽视的陷阱。

两路独立 SIP 对话的主叫/被叫可能同时发 BYE。用全局标志 ByeProcessed 会吞掉第二方的挂断请求。必须为每一侧独立追踪挂断状态，并在双方均确认后立即清理。

B2BUA 模式下，Proxy ACK/BYE 是必要的保底机制。

即使路由正确，网络抖动也可能导致 ACK 丢失。主动代替主叫发 ACK（Proxy ACK）和 BYE 超时重传，是 B2BUA 可靠性的关键保障。

re-INVITE 和 INVITE 重传的 CSeq 差异是区分二者的唯一可靠标准。

运营商在通话建立后可能发 re-INVITE（更新编解码/会话参数），CSeq 会递增。如果 B2BUA 不比较 CSeq，re-INVITE 会被当作重传丢弃，导致运营商 24 秒超时后主动 BYE 挂断。

单个 UDP socket 做双向 RTP 转发是灾难性设计。

NAT 环境下源地址不可靠，初始阶段方向判断极易误判，一旦方向反了就是回声环路。正确做法：每个方向使用独立 socket，或利用 SIPSorcery 原生 RTPChannel。

纯信令 B2BUA 在 NAT 场景下存在天然缺陷——RTP 不通。

外呼 INVITE 的 SDP 中 c= 地址被替换为 OutboundAddress（公网 IP），但 RTP 端口没有 NAT 映射，运营商发的 RTP 包被路由器丢弃。要让媒体流通过，必须实现 RTP 中继或配置端口转发。
