里程碑 项目启动 — C# + SIPSorcery B2BUA

选择方案 1：C# + SIPSorcery 10.0.12 自己写，而非 FreeSWITCH / Asterisk / Kamailio。

核心目标：让分机 8001/8002/8003 在 Android Zoiper 上正确注册、通话、挂断。

设计决策：B2BUA 模式（两侧独立 Call-ID），SDP 透传 + RTP 直连（LAN 场景）。

修复 SIPSorcery 10.0.12 API 差异适配

 SIPProtocolsEnum.UDP            → udp

Bug #1 SendResponse 崩溃 — IPAddress.Parse 无法解析 "IP:Port"
问题

SendResponse 方法中的 IPAddress.Parse(topVia.ReceivedFromAddress) 崩溃。

ReceivedFromAddress 返回的是 "192.168.40.1:5060" 格式（IP:Port），而非纯 IP。

Bug #3 通话建立日志重复 / ACK 无转发日志 / 无音频 / 双端 Android
问题

200 OK 转发给主叫后，被叫的 200 OK 仍持续重传（应用层无去重）；

ACK 从未到达服务端 → 无转发日志；

两个 Android Zoiper 客户端无法建立音频通道。

关键发现

客户端的 ACK/BYE 是根据 200 OK 中的 Contact 和 Record-Route 来路由的。

如果 Contact 指向服务器直连 IP，但客户端在 NAT 后面，ACK 发不到服务器；

如果缺少 Record-Route，客户端可能把 ACK 发到被叫的 Contact 地址而非服务器。

解决

1. 在转发响应中添加 Record-Route 头（使用 AdvertisedAddress），强制后续请求路由到服务器

2. 设置 Callee200OkProcessed=true 实现去重，重传时直接发送缓存的响应

3. 添加 B2BUA 生成的 To tag（B2buaToTag）到所有转发响应

4. 添加服务器 Contact 头到转发响应

Bug #4 8003 摘机仍显示 "Calling" / 挂断不同步 / 日志需求
问题 1

8003 摘机（200 OK）后，8002 仍显示 "Calling" — 说明 200 OK 未正确转发到主叫

问题 2

8002 挂断后 8003 不同步挂断 — BYE 转发/路由失败

问题 3

日志需要输出到 exe 同目录而非控制台

根本发现

SIPSorcery UAS 事务引擎吞噬了 ACK 和 BYE！

在 stateful 模式下，SIPSorcery 的 UAS 事务会自动匹配 ACK/BYE，但不会触发应用层事件。

这意味着 SIPTransportRequestReceived 根本收不到 ACK 和 BYE。

关键修复 切换到 Stateless 模式 — 禁用事务引擎
方案

将 SIPTransport 从有状态模式改为 stateless: true，禁用事务引擎，所有 SIP 消息直接触发应用层事件。

var transport = new SIPTransport(stateless: true, Encoding.UTF8, Encoding.UTF8);
附带问题

Stateless 模式下没有事务层去重，需要自己处理：

• INVITE 重传去重

• BYE 重传去重

• 200 OK 重传去重

• ACK for non-2xx 需要手动发送（原来事务引擎会自动处理）

根因分析 ACK/BYE 路由不到服务器的真正原因
网络拓扑
8002 (192.168.40.100)  ←──同子网──→  服务器 (192.168.40.102)
8003 (192.168.0.110)   ←──NAT──→   路由器 (192.168.40.1) ←──端口转发──→ 服务器
核心问题

AdvertisedAddress = 192.168.40.1（路由器 IP）被用于所有客户端的 Contact/Record-Route。

• 跨子网客户端（8003）：ACK 发往 192.168.40.1 → 端口转发到服务器 ✅

• 同子网客户端（8002）：ACK 也发往 192.168.40.1 → 发到路由器而非服务器 ❌

路由器端口转发是单向的（WAN → LAN），同子网到路由器的 UDP 不会转发回服务器！

次要发现

• 非 2xx 响应（486 BusyHere）也会无限重传 — stateless 模式下没有事务引擎自动发 ACK for non-2xx

• Proxy ACK 延迟约 1.5 秒（等了两次 200 OK 重传才发）

• 主叫的 BYE 同样到不了服务端，导致挂断时只有一端能正常释放

终极修复 四大修复落地 — 智能路由 + 立即 ACK + non-2xx ACK + BYE 超时

根据客户端来源网络选择 Contact/Record-Route 地址：

同子网客户端 (192.168.40.0/24) → Contact = 192.168.40.102 (服务器直连IP)
跨子网客户端 (192.168.0.0/16)  → Contact = 192.168.40.1   (路由器IP)

实现 IsSameSubnet() + GetContactEPForClient()，在 INVITE / 200 OK / BYE / ACK 构建时动态选择地址。

同子网客户端的 ACK/BYE 现在直连服务器 IP，不再绕路到路由器。

修复 2：Proxy ACK 立即发送

首次转发 200 OK 给主叫后，立即发送 Proxy ACK 给被叫。

原来：等重传 #2 才发（延迟 ~1.5 秒）→ 被叫 200 OK 重传 2-3 次

现在：随首次 200 OK 同时发出 → 被叫在 T1 (~500ms) 内收到 ACK，停止重传

修复 3：ACK for non-2xx

新增 SendAckForNon2xxToCallee() 方法。

当收到被叫的 486/487/4xx/5xx 响应时，立即代替主叫向被叫发 ACK for non-2xx，停止重传。

Stateless 模式下 UAS 事务引擎不会自动做这件事，必须手动处理。

修复 4：BYE 超时重传 + 强制清理

HandleBye 不再立即移除会话，改为 CallState.Disconnecting。

清理定时器每 5 秒重传未确认的 BYE（最多 3 次），20 秒后强制清理。

BYE 发出 → 5s 未确认 → 重传 #1 → 5s → 重传 #2 → 5s → 重传 #3 → 5s → 强制清理
总超时 = 20 秒
Bug #5 生产反馈：有几率无法同时挂断
问题

实际部署后反馈：双方同时按挂断时，有几率一方无法成功挂断，仍停留在通话界面。

根因分析

竞态条件 1：ByeProcessed 全局标志导致第二方 BYE 被吞。

原代码用单个 ByeProcessed 标志控制重传去重，但双方同时 BYE 时，第二方的 BYE 是不同 Call-ID 的独立挂断请求，却被当作重传忽略。

8002 BYE (callerCallId) → ByeProcessed=true, 转发 BYE 给 8003
8003 BYE (calleeCallId) → ByeProcessed=true → 当作重传, 不转发

竞态条件 2：BYE 的 200 OK 响应未被处理。

OnSipResponseReceived 只处理被叫 INVITE 响应转发，完全忽略 BYE 的 200 OK。服务端不知道 BYE 是否送达，只能等 20 秒超时强制清理。

修复 双边挂断追踪 + BYE 200 OK 响应处理
修复 1：双边挂断独立追踪

废弃全局 ByeProcessed，改用 CallerHungUp / CalleeHungUp 独立追踪两侧挂断状态。

BYE 到达时只标记对应侧已挂断，仅当另一侧尚未挂断时才转发 BYE。

8002 BYE → CallerHungUp=true, 转发 BYE 给 8003
8003 BYE → CalleeHungUp=true, 不重复转发 (8002已挂)
双方均 HungUp → 立即清理会话
修复 2：BYE 200 OK 响应处理

新增 HandleBye200Ok() 方法，在 OnSipResponseReceived 中识别 BYE 的 200 OK。

收到后标记 Bye200OkReceived=true，停止重传，并标记对端已挂断。若双方都已挂断，立即清理会话。

服务器发 BYE → 对端回 200 OK → Bye200OkReceived=true → 确认送达, 停止重传
里程碑 SIP Trunk 外呼 — 对接中国电信 IMS

新增 SipTrunkManager.cs 模块，实现与运营商 SIP Trunk 的对接，让内机拨打外线号码（按 9 出局）。

核心功能

1. REGISTER 注册：向运营商 P-CSCF (172.26.160.38) 注册 Trunk 号码，含 401 Digest 重认证

2. 外呼 INVITE：内机按 9 出局时，B2BUA 向运营商发起 INVITE，含 SDP 透传

3. 183 Session Progress：运营商返回早期媒体（回铃音/语音提示），透传给内机

4. 入站 INVITE：运营商呼入时，DID 映射到内机并振铃

5. 呼叫转移：Busy / NoAnswer / Unconditional 三种转移模式

6. DTMF：SIP INFO 方式的 DTMF 透传

遗留问题

纯信令 B2BUA 模式下，外呼 INVITE 的 SDP 中 c= 地址被替换为 OutboundAddress (172.48.242.167)，但 RTP 端口没有路由器 NAT 转发 → 运营商往公网 IP 发的 RTP 包被路由器丢弃 → 内机听不到早期媒体/语音提示。

Bug #6 外线通话 BYE 路由错误 — Request-URI 指向自身
问题

外线通话中，运营商发 re-INVITE 后 BYE 路由出错。被叫侧挂断时，AsterTele 向主叫侧发 BYE 的 Request-URI 用了 session.CallerInvite.URI，指向自己的 Contact 地址而非运营商的 Contact。

同时，入站通话中运营商发 re-INVITE（更新会话参数），被错误当作 INVITE 重传处理，导致运营商 24 秒后主动 BYE 挂断。

根因分析

BYE 路由：B2BUA 构造 BYE 时未使用对方在 200 OK/Contact 中声明的地址，而是用了 INVITE 的原始 URI。当通话经过 re-INVITE 后，运营商的 Contact 可能已变化。

re-INVITE 误判：HandleInvite 中 existingByCaller!=null 分支无条件走重传逻辑，没有做 CSeq 比较。CSeq 递增的 re-INVITE 被当作 CSeq 相同的重传直接丢弃。

修复 1：缓存 Contact URI

在 CallSession 中新增 CallerContactUri / CalleeContactUri 字段，在创建会话时（CreateSession）和收到 200 OK 时（ForwardCalleeResponse）保存运营商/被叫的 Contact URI。

SendByeToCaller 和 SendByeToCallee 使用缓存的 Contact URI 构造 BYE 的 Request-URI。

修复 2：CSeq 区分 re-INVITE 与重传

在 CallSession 中缓存原始 INVITE 的 CSeq（CallerInviteCSeq 字段）。HandleInvite 的 existingByCaller 分支中：

CSeq 相同 → 重传, 重发最后响应
CSeq 递增 → re-INVITE, 调用 HandleTrunkReInvite
修复 3：路由集 (Route Set) 支持

SendByeToCaller / SendByeToCallee 构造 BYE 时，按 RFC 3261 将 SIPRouteSet 的 reversed 路由集添加为 Route 头，确保 BYE 沿原对话路径路由回运营商。

Bug #7 RTP 中继方案 — 回声环路，实测失败并回滚
问题

为解决「内机打外机，外机拒接时内机听不到提示音」的核心问题，实现了完整的 RTP 中继方案：RtpRelaySession.cs（双向 RTP/RTCP UDP 转发）+ SdpModifier.cs（SDP 修改工具）。

实测结果：只能听到自己说的话（回声/环路），相当于 TX/RX 短接。

失败根因分析

单 socket 双向转发的方向判断不可靠。

RtpRelaySession 用一个 RTP socket 接收双方包，通过 IsFromCaller() 判断方向后转发。但：

1. 初始阶段（双方都未发送过包时），方向默认假设「来自分机侧」，第一个到达的包方向可能误判

2. NAT 环境下源地址不可靠，内机经 NAT 后的源端口与 SDP 声明端口不一致

3. 方向一旦误判，后续所有包都沿错误方向转发，形成回声环路

处置：完整回滚

删除了 RtpRelaySession.cs 和 SdpModifier.cs，CallManager.cs / SipSoftSwitch.cs / SipOptions.cs / appsettings.json / Program.cs 均恢复原状。编译验证通过，0 错误 0 警告。

里程碑 RTP 媒体锚定 — 双 socket NAudio 方案，从纯信令升级为媒体 B2BUA

为彻底解决「外呼拒接时内机听不到运营商忙音/语音提示」的核心问题，采用 NAudio 实现双 socket RTP 媒体锚定。

架构设计

   │  RTP (G.711 A-law)             │  RTP (G.711 A-law)

Bug #8 RTP SDP 地址 0.0.0.0 — UdpClient 监听在 0.0.0.0 导致地址不可达
问题

NaudioRtpBridge 中 _ctx.LocalEP.Address 返回 0.0.0.0（因为 UdpClient 监听在 0.0.0.0），导致 SDP 的 c= 字段填入 0.0.0.0，运营商 RTP 包无处可达。

修复

在 RtpOptions 中新增 MediaAddress 配置项（默认值 192.168.40.102），SDP 锚定时优先使用 MediaAddress，不再从 socket 本地地址推断。

Bug #9 RTP 地址学习方向反了 — 双方都发回给自己
问题

_callerRecvTask 收到主叫的 RTP 包后，应学习主叫的实际地址存入 _callerRemoteEP，但代码误存为 _calleeRemoteEP。结果：

• 主叫包到达 → 学习地址存入 calleeRemoteEP → 把主叫包转发给运营商（正确）

• 运营商包到达 → 学习地址存入 callerRemoteEP → 把运营商包转发回主叫（正确）

• 但下次主叫包到达时，转发目标取 callerRemoteEP（已存运营商地址）→ 主叫包发给运营商了 ✅

• 下次运营商包到达时，转发目标取 calleeRemoteEP（已存主叫地址）→ 运营商包发给主叫了 ✅

看似「歪打正着」？实际端口号也不对——见 Bug #10。

修复

修正地址学习方向：_callerRecvTask 学习 _callerRemoteEP，_calleeRecvTask 学习 _calleeRemoteEP。语义清晰，不再依赖巧合。

Bug #10 RTP 地址学习端口错误 — NAT 同时改写 IP 和端口
问题

地址学习代码用 getDest()?.Port（SDP 声明的转发目标端口）拼上 result.RemoteEndPoint.Address（实际源 IP），构造出 实际源IP:SDP声明端口 的错误组合。

但路由器 NAT 同时改写 IP 和 端口，实际源端口 ≠ SDP 声明端口。拼接出的端点地址在 NAT 后永远不正确。

修复

直接使用 result.RemoteEndPoint（完整的实际源地址，包含 NAT 后的真实 IP 和端口），不再拼凑。

Bug #11 RTP 关闭时 SocketException 995 — Windows OperationAborted 未捕获
问题

RTP 会话结束后 Dispose 关闭 UdpClient，在 Windows 上触发 SocketException 错误码 995 (SocketError.OperationAborted)。

原代码只 catch SocketError.Interrupted（Linux），Windows 上的 995 未被捕获，导致异常冒泡到日志。

修复

Bug #12 短号/服务号拨号失败 — 10000 被加 +86 前缀导致运营商拒绝
问题

拨号规则 StripPrefix=true，拨 910000 → 剥离前缀后得到 10000。

代码逻辑：if (!outboundNumber.StartsWith("+") && outboundNumber.Length >= 5) outboundNumber = "+86" + outboundNumber;

修改后: if (Length >= 7) → 加 +86   // 10000 不再加, 手机号正常加

    option dest 'lan'

RTP 地址学习需要收到第一个包才能确定远端地址。在学习完成前，转发目标端点为 null，首个 RTP 包被直接丢弃。

                                → 否: 入队列 + 尝试学习地址

Bug #17 本地通话 BYE 跟挂失败 — Route 指向自身 + Request-URI 用 NAT 内网地址
问题

8002(Zoiper)挂断后，BYE 转发给 8001(DAG1000) 仍不跟挂。对比旧版 Gitee 代码（正常工作）发现 BYE 构建逻辑存在两处关键偏差。

根因1（高概率）：Route 头错误地指向 AsterTele 自身

ByeHandler.SendByeToCallee 将 INVITE 的 Record-Route 复制为 BYE 的 Route 头。但 AsterTele 是被叫侧 dialog 的 UAC，按 RFC 3261 §12.1.2，UAC 的路由集应来自 200 OK 响应的 Record-Route（反转），而非 INVITE 的 Record-Route。

本地设备（DAG1000/Zoiper）的 200 OK 不含 Record-Route，所以路由集应为空。当前代码把 Record-Route: sip:192.168.40.102;lr 拷贝进 BYE Route 头，指向 AsterTele 自身，导致 SIPSorcery 可能按 Route 发回 AsterTele 或 DAG1000 无法匹配 dialog。

旧版代码不在本地通话 BYE 中添加 Route 头，所以不会有此问题。

根因2（中概率）：Request-URI 用了 NAT 内网地址

当前代码 SendByeToCallee 优先使用 session.CalleeContactURI（来自 DAG1000 的 200 OK Contact），对于 NAT 后的设备，200 OK Contact 是内网地址（如 192.168.0.149），从 AsterTele 侧不可达。

旧版代码始终使用 session.CalleeInvite.URI（即 INVITE 的 Request-URI，也就是注册的 Contact URI，经 SNAT 后的 192.168.40.1:11345），这个是可达的。

修复1：本地通话 BYE 不添加 Route 头

SendByeToCallee：只有外呼 Trunk 通话才复制 Record-Route 为 Route（运营商 SBC 需要路由）；本地通话跳过 Route 设置。

SendByeToCaller：只有入站 Trunk 通话才添加 Route 头（运营商 INVITE 的 Record-Route 指向运营商 SBC）；本地/外呼通话跳过 Route 设置。

修复2：本地通话 BYE Request-URI 改回 CalleeInvite.URI

本地被叫方向，BYE Request-URI 使用 session.CalleeInvite.URI（INVITE 的 Request-URI，即注册时的 Contact URI），不再使用 200 OK Contact（可能含 NAT 内网地址不可达）。

外呼 Trunk 方向保持不变，仍优先使用 session.CalleeContactURI（运营商 200 OK Contact）。

NaudioRtpBridge 中新增 ConcurrentQueue<byte[]> 缓冲机制：地址学习完成前收到的 RTP 包入队列，学习完成后 FlushPendingPackets() 批量转发。队列最大容量 50 包，防止内存泄漏。

⑬ BYE 跟挂修复 (LocalEP)

SipSoftSwitch 的 _localEP 优先使用 MediaAddress 配置值 (192.168.40.102)，不再用 GetLocalIPv4() 自动探测（多网卡/VPN 适配器会选错）。修复后同子网客户端的 BYE/ACK 正确发到服务器直连地址。

⑮ BYE Route/Request-URI 修复

本地通话 BYE 不再添加 Route 头（AsterTele 是 UAC，路由集来自 200 OK Record-Route，本地设备 200 OK 不含 Record-Route）；本地通话 BYE Request-URI 改回 CalleeInvite.URI（注册 Contact 可达），不用 200 OK Contact（NAT 内网地址不可达）。仅 Trunk 通话保留 Route 头和 ContactURI 逻辑。

⑭ Via/REGISTER/外呼 INVITE 地址统一修复

CreateB2BUAInvite 中 Vias.Via.Clear() 去重；REGISTER Contact/Via 改用 outboundIp；外呼 INVITE From host 用 clientUriHost，Contact/Via 用 trunkOutIp。消除所有 GetLocalIPv4() 在运营商侧的使用。

路由器防火墙默认只放行 SIP(5060)，RTP 端口(10000-60000)被 DROP。添加 Allow-RTP-LAN1-LAN2 规则允许 UDP 10000-60000 从 LAN1 转发到 AsterTele。配置后 8001→8002 双向音频正常。

💡 关键经验教训

SIPSorcery stateless 是必需的，但代价是自己处理一切去重。

Stateful 模式下 UAS 事务引擎吞噬了 ACK/BYE 事件，但自动处理了去重、重传、non-2xx ACK。切换到 stateless 后这些都要自己实现。

AdvertisedAddress 不是万能的——同子网客户端不需要 NAT 地址。

一刀切地把所有 Contact/Record-Route 设为路由器 IP，会让同子网客户端的 ACK/BYE 错误路由到路由器。必须按客户端网络拓扑动态选择。

Via 头不能替换——客户端用它匹配 INVITE 事务。

曾尝试替换 Via 为服务器地址来路由 ACK，结果客户端无法匹配 200 OK → 通话完全无法建立。Via 必须保留原始 INVITE 的值。

双边 BYE 竞态是 B2BUA 最容易忽视的陷阱。

两路独立 SIP 对话的主叫/被叫可能同时发 BYE。用全局标志 ByeProcessed 会吞掉第二方的挂断请求。必须为每一侧独立追踪挂断状态，并在双方均确认后立即清理。

B2BUA 模式下，Proxy ACK/BYE 是必要的保底机制。

即使路由正确，网络抖动也可能导致 ACK 丢失。主动代替主叫发 ACK（Proxy ACK）和 BYE 超时重传，是 B2BUA 可靠性的关键保障。

re-INVITE 和 INVITE 重传的 CSeq 差异是区分二者的唯一可靠标准。

运营商在通话建立后可能发 re-INVITE（更新编解码/会话参数），CSeq 会递增。如果 B2BUA 不比较 CSeq，re-INVITE 会被当作重传丢弃，导致运营商 24 秒超时后主动 BYE 挂断。

单个 UDP socket 做双向 RTP 转发是灾难性设计。

NAT 环境下源地址不可靠，初始阶段方向判断极易误判，一旦方向反了就是回声环路。正确做法：每个方向使用独立 socket，彻底避免方向判断。

RTP 地址学习不能拼凑——NAT 同时改写 IP 和端口。

用「SDP 声明端口 + 实际源 IP」拼凑远端地址在 NAT 后必错。路由器 NAT 会同时重写 IP 和端口，必须直接使用 RemoteEndPoint 的完整地址。

UdpClient 监听 0.0.0.0 时，LocalEP.Address 就是 0.0.0.0，不能用于 SDP。

必须显式配置 MediaAddress（实际可达的 IP 地址），用于 SDP 的 c= 字段。在 NAT 环境中这个地址可能是内网 IP（对本地分机）或外网 IP（对运营商）。

Windows 和 Linux 的 Socket 关闭行为不同——OperationAborted vs Interrupted。

Windows Dispose UdpClient 触发 SocketError.OperationAborted (995)，Linux 触发 SocketError.Interrupted。跨平台代码必须同时处理两者。

短号/服务号的号码格式规则与常规号码不同。

中国电信 IMS 中，短号/服务号（110、119、120、10000、10086 等，≤6位）不加国际前缀 +86；常规号码（手机号 11 位、固话 7-12 位，≥7位）才加 +86。号码格式化逻辑必须区分两者。

路由器防火墙不只管 SIP，RTP 端口也要显式放行。

OpenWrt 默认防火墙配置只放行了 SIP (5060) 端口。RTP 媒体流使用动态端口范围 (10000-60000)，如果不显式添加放行规则，跨子网的 RTP 包会被路由器静默 DROP。这个问题没有错误日志，只能通过 UDP 监听实测验证。

NAT 环境下直连 RTP 是不可行的——SDP 地址和实际源地址永远对不上。

DAG1000 经路由器 SNAT 后，SDP 声明的 IP (192.168.0.149) 对 AsterTele 不可路由；反过来 AsterTele 发 RTP 到 DAG1000 的内网 IP 也不可达。即便尝试绕过 B2BUA 直接连接，NAT 映射地址反射也会导致回声。唯一可行方案：所有通话走 RTP 锚定 + NAT 感知 SDP 地址。

RTP SDP 地址必须按客户端网络位置动态选择——一刀切必出问题。

同子网客户端用 MediaAddress 直连服务器，跨子网/NAT 客户端用 AdvertisedAddress 经路由器转发。如果给跨子网客户端用 MediaAddress，RTP 包被路由器防火墙阻止；如果给同子网客户端用 AdvertisedAddress，增加不必要的路由跳数。必须按 IsSameSubnet() 动态判断。

RTP 地址学习的首包丢包可以用缓冲队列优雅解决。

地址学习需要收到第一个 RTP 包才能确定远端地址，在此之前的包无处可发。用 ConcurrentQueue 缓冲这些包，地址学习完成后批量刷新，既不丢包也不阻塞。

监听 0.0.0.0 时 LocalEP.Address 就是 0.0.0.0——不能用于子网判断。

UdpClient 绑定 0.0.0.0 时，LocalEP.Address 恒为 0.0.0.0，导致 IsSameSubnet 永远返回 false，所有客户端被当作跨子网处理。必须用显式配置的 MediaAddress 初始化 _localEP。

GetLocalIPv4() 在多网卡环境下不可靠——VPN/虚拟适配器会干扰。

Windows 电脑通常有多个网络适配器（Wi-Fi、以太网、VPN、Hyper-V 虚拟交换机等），GetLocalIPv4() 可能返回非预期的 IP 地址。SIP 服务器地址必须显式配置，不能依赖自动探测。所有运营商侧地址（REGISTER Contact/Via、外呼 INVITE From/Contact）都用 outboundIp / clientUriHost / trunkOutIp，消除对 GetLocalIPv4() 的依赖。
